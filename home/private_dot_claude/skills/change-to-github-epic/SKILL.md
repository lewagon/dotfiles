# Change → GitHub Epic

Converts an OpenSpec change proposal into a structured GitHub epic: linked
issues, a dependency-ordered roadmap, and a developer resource mapping —
drafted for review, never created without explicit confirmation.

## When to use this skill

Run this at the handoff between planning and building. This is planning
work, not implementation — the goal is to translate an already-drafted
plan into something the team can plan a sprint around. Three entry points:

| Source | Run after | Run before | Plan lives in |
|---|---|---|---|
| OpenSpec | `/opsx:propose` (or `/opsx:ff`, `/opsx:continue` once apply-ready) | `/opsx:apply` | `openspec/changes/<name>/` |
| SpecKit | `/speckit.tasks` (ideally `/speckit.analyze` too) | `/speckit.implement` | `specs/<NNN-name>/` (`spec.md`, `plan.md`, `tasks.md`) |
| Claude Code plan session | the plan is approved (plan mode exit) | the first edit | the approved plan (conversation, or the saved plan file) |

**Be proactive.** When one of these workflows reaches its finish line,
offer this skill before the next step starts, even if the user didn't ask
and even if the change looks small. Skipping it at the handoff is the usual
failure: the next command (`/opsx:apply`, `/speckit.implement`, or the first
edit) starts the build with no issues to track it against. Offer once and
accept a "no" — never block the next step.

Do not run this on a plan that hasn't been finished, and do not run it as
a substitute for `/opsx:apply`, `/speckit.implement` or any other
implementation step — this skill never writes code.

**Why the trigger is only best-effort.** A description can be recognized
and still skipped, and the keys this skill can use (`when_to_use`) only
improve matching. A skill's own `hooks:` run only after it has loaded, so
they can't enforce loading. Hard enforcement belongs in a hook in
`settings.json`, for example a `PostToolUse` hook on `ExitPlanMode` or a
`UserPromptSubmit` hook matching `/opsx:apply` and `/speckit.implement`
that reminds the model to run this skill first. Explicit `/change-to-github-epic`
always works.

**Claude Code only.** This skill runs `git`/`gh` via shell and reads the
change folder directly from the local filesystem, so it needs real bash
and filesystem access to the project's working tree. Plain Claude Desktop
chat has neither and will fail before it can even resolve which change to
use. It could in principle run inside Cowork (which does have shell and
filesystem access), but only if that exact repo — with the OpenSpec
change folder already generated by `/opsx:propose` — is present in the
Cowork workspace, which usually isn't the case.

## Resolving which change

- If invoked with an argument naming a change (or given a path), use that
  directly.
- Otherwise detect the source. OpenSpec: list changes (e.g.
  `openspec list --json`) and find ones whose planning artifacts are
  complete (apply-ready). SpecKit: look for `specs/*/tasks.md` (and
  `.specify/`). Plan session: use the plan just approved in this
  conversation. If exactly one candidate matches, use it. If zero or more
  than one match, ask the user which to use before reading any files —
  don't guess from conversation context alone if it's ambiguous.

## Inputs

Read, in this order, from the relevant source. The headings below map the
three sources onto the same roles; the rest of the skill refers to the
roles ("scope", "design", "tasks", "requirements").

**OpenSpec** (`openspec/changes/<name>/`):

1. `proposal.md` — scope, intent, what's in/out
2. `design.md` — technical approach; the primary source for dependency detection
3. `tasks.md` — the ordered task list; source material for individual issues
4. `specs/` (delta specs) — cross-check that no requirement is missing an issue

**SpecKit** (`specs/<NNN-name>/`):

1. `spec.md` — scope, user stories, acceptance scenarios (the "what")
2. `plan.md` (+ `research.md`, `data-model.md`, `contracts/`) — technical approach; the primary source for dependency detection
3. `tasks.md` — the ordered task list with `[P]` parallel markers and phases; source material for issues (`[P]` tasks hint at same-wave work)
4. `.specify/memory/constitution.md` — constraints every issue must respect; cross-check, don't copy

**Claude Code plan session:** the approved plan is the only input. Treat
its goal as scope, its steps as tasks, and its stated ordering as the
dependency source. There are no spec files to cite, so each issue's
reference back to the source is the plan file path if one was saved
(otherwise a short plan excerpt in the issue body). Say in the draft that
acceptance criteria were inferred from the plan, not from a spec.

If a project-level `CLAUDE.md` or `AGENTS.md` contains a team/ownership
section (developer names mapped to domains, e.g. "creators/ → Dev B"), read
it too — this is the source for the resource mapping step. If no such
section exists, produce the roadmap without assigning names, and flag
that ownership mapping needs manual input.

## Determining the target repo and project

- Confirm the target GitHub repo from the change's working tree, e.g.
  `git remote -v`. If there's exactly one remote, use it. If there are
  multiple remotes, or none, ask which repo the issues should live in —
  don't default to guessing.
- Confirm the target GitHub Project (the board, e.g.
  `github.com/users/<owner>/projects/<n>`) from what the user names
  explicitly — a URL or a title. If none was given, ask; don't assume a
  default project.

## Workflow

### 1. Draft the epic

Read `references/epic-writing.md` first. It holds the body template, the
mapping from OpenSpec, SpecKit and plan inputs to each section, the slicing
rules and a quality checklist.

The epic is the parent issue for one deliverable outcome. It leads with why
and when it is done, links to the spec instead of copying it, and carries
what only GitHub can hold: order, ownership and project state. Compose it
from steps 2–5, in this order:

- **Title:** `Epic: <change name in plain language>` (not the kebab-case folder name). Sub-issues never use the word "Epic".
- **Goal:** the problem or opportunity and why now, in one or two sentences (OpenSpec "Why", SpecKit story value, or the plan's goal)
- **Done when:** two to five measurable exit criteria, each checkable by a test, command or observation (SpecKit `SC-xxx` and Independent Tests, OpenSpec delta-spec scenarios). If the source has none, say so; never invent one.
- **Scope:** in and out, from the source
- **Source of truth:** the path to the change, spec or plan, and the source type
- **Roadmap:** the wave table from step 4, with owner and "needs" columns (this carries the dependency map from step 3 in readable form)
- **Risks and open questions:** only real ones from the source; omit if none
- **Project automation:** enabled and disabled workflows

Do not write a checkbox list of the sub-issues into the body. GitHub's
native sub-issue progress on the parent and in the project shows completion
and stays correct, while a hand-kept list drifts.

**Sizing check before drafting.** Count the issues and estimate effort
first, because it decides whether an epic is the right shape at all.

- **Under about three issues or a few days: ask first.** Stop before
  writing the full epic and put one short question to the user: "This is
  about N tasks (hours of work). An epic with one sub-issue is more
  structure than it needs. Do you want (a) a single issue with the tasks
  as a checklist, or (b) the full epic anyway?" Wait for the answer. On
  (b), continue as normal. On (a), draft one issue (Goal, Done when and
  Source of truth in a short body, the task checklist, acceptance
  criteria) and go straight to "Present and stop". The user asked for an
  epic, so never decide this for them and never refuse.
- **More than about fifteen issues or several quarters:** propose
  splitting into several epics, one per deliverable outcome, in the
  Sizing line of the draft, and still draft the epic so the user can
  compare.
- **Otherwise:** no question, just the one-line result.

Whatever the result, it becomes the first line of the draft (see the
Output format), above the epic, not in the Notes section.

The epic should be readable top to bottom as the single place the team goes
to understand what is being built, why, in what order and by whom, without
opening every linked issue first.

### 2. Convert tasks into issues

Walk `tasks.md` top to bottom, but do not copy its section headings into
issues. In OpenSpec those headings are usually layers (data, rendering,
UI), and a layer ships nothing a user can check until every layer is done.
Cut by outcome instead (full rules in `references/epic-writing.md` §4):

- **One issue per spec requirement or user story.** Map each OpenSpec
  delta-spec requirement and each SpecKit user story to one issue, and put
  the tasks that deliver it in that issue, whichever `tasks.md` section they
  sit in. Show the mapping in the draft.
- **Enabler issues are allowed, but named.** Shared setup that several
  slices need (a migration, a token helper) is its own issue, titled as an
  enabler and saying which slices it unblocks. Do not create an enabler
  per layer of one slice.
- **Fall back to `tasks.md` grouping** only when there is no requirement or
  story to map to (plan sessions, or tasks outside any requirement such as
  cleanup). Group related sub-tasks into one reviewable unit, and don't
  create one issue per checklist line.

Each issue should include:

- A title derived from the task
- Acceptance criteria pulled from the corresponding spec scenarios (OpenSpec
  WHEN/THEN, SpecKit Given/When/Then), so the issue is done when its
  scenarios pass. Cut issues by outcome (a SpecKit user story, an OpenSpec
  capability), not by layer, and keep the test task ahead of the
  implementation task in the checklist.
- A reference back to the source (the OpenSpec change folder, the SpecKit
  `specs/<NNN-name>/` folder, or the saved plan file), so reviewers can
  trace the issue to where it came from
- The task checklist for that issue, copied from `tasks.md` (or the plan
  steps). Add one line under it: "Copied from `<path>` — the source file
  stays the source of truth; this list can drift."

**Every issue gets relationships**, set at creation, not left in prose:

- **Parent** (always): the epic. The epic itself is the only issue without one.
- **Blocked by / blocking** (when a dependency from step 3 exists).
- **Relates to** (when applicable): issues in the same domain that share
  files or context but have no technical ordering. GitHub has a native
  "Relates to" relationship (generally available since 2026-09-25), set
  with the GraphQL `addRelatesTo` mutation because `gh` has no flag for it
  (see "Creating the epic and issues in GitHub"). If that call fails, fall
  back to `Related: #n` in the issue body, which still cross-references
  both ways, and say so in the draft.

### 3. Identify dependencies

Read `design.md` for technical ordering constraints (e.g., "requires the
new `creators` table migration before the profile UI can be built"). Two
issues are dependent if one's implementation is a technical prerequisite
for the other, not merely if they're related in subject matter. Record
dependencies explicitly, issue-to-issue — this feeds directly into both
the epic's dependency section and the wave grouping in step 4, and into
the native blocked-by/blocking links created in "Creating the epic and
issues in GitHub" below.

### 4. Propose a wave-based roadmap

Group issues into waves:

- **Wave 1** — issues with no dependencies; can start immediately, in parallel
- **Wave 2+** — issues that depend on a prior wave's completion

Within a wave, issues touching different OpenSpec domains (see the spec's
domain folder, e.g. `creators/`, `auth/`) can run in parallel; issues
touching the same domain should generally be sequenced to avoid merge
conflicts, even without a hard technical dependency.

### 5. Suggest resource mapping

If ownership information was found in step 1 (Inputs), map each issue to
the developer who owns that domain. If a domain has no established owner,
leave it unassigned and flag it rather than guessing. This same
never-guess rule applies to any other project field that represents a
judgment call (priority, effort, due dates) — see Explicit boundaries.

### 6. Present and stop

Output the full epic — with goal, done-when criteria, scope, roadmap
(carrying dependencies and owners) and project automation in its body as
described in step 1 —
as a single reviewable block. **Do not create anything in GitHub yet.**
End the turn here and wait for explicit confirmation on:

- The epic and issue breakdown itself (is the grouping right?)
- The proposed roadmap and wave sequencing
- The resource assignments, especially any that were guessed rather than
  sourced from an ownership doc

Only after explicit confirmation, proceed to create the epic and issues
in GitHub as described below.

**Carry open Notes into the epic.** The draft's Notes section is for
review and is never written to GitHub, so a flag left only there is lost
once the epic exists. Before creating, go through Notes: anything the user
resolved or accepted as is drops out; anything still open (a dependency
that stays a guess, an acceptance criterion inferred rather than sourced,
a spec requirement with no task, an unassigned owner the user chose to
leave) moves into the epic's "Risks and open questions", one line each,
so the next reader sees what was never settled. Resolved items are not
carried over, and neither is the Sizing line, which is a review aid.

## Output format

Present the draft in this structure so it's easy to scan and approve or
correct piece by piece. Note that everything nests inside the epic —
there is no separate top-level roadmap or resource section:

```markdown
**Sizing:** <N issues from M tasks, effort in days or weeks; "normal epic range", "small: single issue offered" or "large: split proposed">

## Epic: <title>

### Goal
<why, one or two sentences>

### Done when
- [ ] <measurable criterion> (source: SC-001)

### Scope
**In:** ... **Out:** ...

### Source of truth
<path> — <OpenSpec | SpecKit | Plan session>

### Roadmap
| Wave | Issue | Owner | Needs |
|---|---|---|---|
| 1 (parallel) | #1 <title> | <owner or "unassigned"> | none |
| 2 | #2 <title> | unassigned | #1 |

### Risks and open questions
- ...

### Project automation
Enabled workflows: ... Disabled: ... (what happens automatically vs by hand)

### Notes (in the draft only, not the issue body)
- Unassigned issues, guessed dependencies, criteria inferred rather than sourced.
  Review only: whatever is still open after confirmation moves into the epic's "Risks and open questions".
```

Each sub-issue is shown beneath the epic with its title, parent, blocked-by,
`Related:` links and acceptance criteria, as in step 2.

## Creating the epic and issues in GitHub

Once the draft is confirmed, prefer the GitHub CLI (`gh`) when it's
available and authenticated (`gh auth status`). Use GitHub's native
relationship features rather than tracking structure only in prose:

- `gh issue create --parent <epic-number>` links a sub-issue to the epic
  natively (populates GitHub's own sub-issue progress, not just a
  hand-written checklist).
- `gh issue create --blocked-by <n1,n2>` (or `--blocking`) encodes the
  dependency map from step 3 as real tracked relationships.
- `gh issue create -p "<project title>"` (or `--project`) adds the issue
  to the target project in the same call.
- "Relates to" has no `gh` flag. Once both issues exist, look up their
  node ids (`gh issue view <n> --json id --jq .id`) and call
  `gh api graphql -f query='mutation($a:ID!,$b:ID!){addRelatesTo(input:{issueId:$a,relatedIssueId:$b}){clientMutationId}}' -f a=<id> -f b=<id>`
  for the first pair only. Read both issues back (`Issue.relatesTo` via
  `gh api graphql`) to see whether the link shows on both sides; if it
  does, one call per pair is enough, otherwise add the reverse call. Then
  do the rest. On any error use the `Related: #n` fallback.
- GitHub allows at most 50 links per relationship type per issue (blocked
  by, blocking). Split an issue that would exceed that.

**Creation order matters.** The epic has no parent and must be created
first. Each sub-issue can then set `--parent` to the epic's number.
Walk the wave order from step 4 — GitHub rejects a dependency on an issue
that doesn't exist yet, so an issue with `--blocked-by` deps must be
created after the issues it depends on. The order is derived from the
dependency map, not chosen: if D depends on C, C is created first, and an
issue that depends on everything is created last. Wave order alone is not
enough when two issues in the same wave depend on each other.

**What the project workflows do versus what this skill does.** Project
workflows (the board's Workflows tab) are enabled per project, and the
template project has them on. Check which are enabled for the target
project before creating anything, because it decides what the skill must
do by hand:

```
gh api graphql -f query='query($o:String!,$n:Int!){user(login:$o){projectV2(number:$n){workflows(first:30){nodes{name enabled}}}}}' -f o=<owner> -F n=<project-number>
```

(Use `organization(login:$o)` instead of `user` for an org-owned project.)

| Workflow (template defaults) | Effect | Skill's job |
|---|---|---|
| Auto-add sub-issues to project | sub-issues of an epic already on the board join it | add only the epic with `-p`; verify the children arrived |
| Auto-add to project | new repo issues matching a filter join | nothing, if enabled |
| Item added to project | sets Status (usually Backlog) | do not set Status; read it back |
| Item closed / reopened, Auto-close issue, Auto-archive items | status follows issue state | nothing |
| Pull request linked to issue / merged, Code changes requested | status follows PR state | nothing |

If a workflow is disabled, do its job by hand, and only for fields with an
obvious default (add each issue with `-p`; Status only if the project
defaults to none). Put the enabled/disabled list in the draft so the user
sees what will and won't happen automatically. Never set Priority, Effort
or due dates either way.

**The epic body has a chicken-and-egg problem.** It can't link real issue
numbers until the sub-issues exist, but the sub-issues want `--parent`
pointing at the epic, which must exist first. Resolve this in two passes:
create the epic first with a placeholder note in place of the
issue/roadmap/dependency sections (e.g. "sub-issues and roadmap to be
filled in once created"), create all sub-issues against it, then
`gh issue edit <epic-number>` to rewrite the body with the real issue
numbers in the Roadmap table, per the Output format template. The Goal,
Done when, Scope and Source sections can go in at creation; only the
Roadmap needs the second pass.

**Custom project fields.** Check what fields the target project has (e.g.
`gh project field-list <n> --owner <owner>`) and what a newly added item
defaults to (`gh project item-list <n> --owner <owner>`) before setting
anything manually — many projects already default new items into a
sensible "not started" status. Only set fields with an obvious,
non-judgment default. Never set Priority, Effort, due dates, or any other
field representing a business/personal judgment call without an explicit
source — same rule as resource mapping in step 5, generalized to any
custom field, not just developer names.

## Verification

After creating the epic and all issues, confirm the sequence actually
completed rather than assuming it did — an interrupted or partially
failed run should never be reported as a clean success:

Run these checks, read back through the API rather than assumed from the
create calls, and report each as pass or fail with the numbers:

- **Parent links:** every child lists the epic as its parent (native
  sub-issue link). `gh issue view <epic-number> --json subIssuesSummary`
  must report a total equal to the planned issue count, so GitHub shows
  the progress itself.
- **Dependencies:** the blocked-by links match the plan exactly, in both
  directions, for every issue, not just a spot-check.
- **Coverage:** every task from `tasks.md` (or plan step) appears in
  exactly one issue. State the count per issue and the total, e.g.
  `6+3+4 = 13 of 13 tasks`. Zero or two appearances is a failure.
- **Assignee:** each issue is assigned as drafted. If the draft left
  owners unset, they must be unset.
- **Status and fields:** the board item for each issue (epic and children)
  has the Status the project workflows were expected to give it, and
  Priority, Effort and due dates are untouched. Report what the workflows
  actually did.
- **Title:** the epic's title contains "Epic".
- **Epic body:** it has Goal, Done when and Source of truth; every Roadmap
  row names a real issue number that is a sub-issue of the epic; and no
  placeholder text is left. Read the body back with `gh issue view`.

Report the epic URL and each issue's URL/number back to the user; if
anything failed to create or link, say so explicitly rather than
omitting it from the summary, and never report a partial run as success.

## Assignees

If the ownership section from Inputs exists, use it. If it doesn't and the
target repo is a personal repo owned by the authenticated user (`gh api
user --jq .login` equals the repo owner), propose assigning every issue to
that user in the draft, and mark it as a proposal for confirmation. For a
shared or org repo with no ownership source, leave issues unassigned.

## Explicit boundaries

- Never call any GitHub-creating action before the person has reviewed
  and confirmed the draft.
- Never guess a developer's ownership assignment, a priority, an effort
  estimate, or any other project field that represents a judgment call —
  always flag these as unset/unassigned instead of presenting them as
  settled.
- Never guess which repository or which GitHub Project to file into —
  resolve explicitly (see "Determining the target repo and project") or
  ask.
- Never use this skill to skip or replace `/opsx:apply`,
  `/speckit.implement` or the build of an approved plan — it produces
  planning artifacts for the team, not code.
- The change files (or plan) stay the source of truth. The checklists in
  the issues are copies and can drift; when they disagree, the source wins.
  Issue checkboxes tick as the work is done.
